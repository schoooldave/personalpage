# 《系统不等于流程》文章设计

## 定位

第三篇文章讨论系统与真实业务流程之间的边界。它不复述第一篇的数据价值链，也不重复第二篇的上线采用问题，而是回答：为什么系统里的步骤都正确，到了现场仍然需要判断、协调和绕行。

## 核心判断

> 系统可以承载流程，但不能自动生成流程。真实流程还包括判断、例外处理、角色协同和责任承接。

## 内容结构

### 开篇对照

用“系统里的步骤 / 真实业务的关系”做一组直接对照：系统记录提交、审批、完成；真实业务还需要判断、处理例外和承担责任。

### 三个断点

1. **判断不是点击**：系统可以要求填写和提交，但不能自动理解现场问题属于哪种情况，也不能替用户选择正确路径。
2. **例外不是错误**：渠道、组织和门店关系持续变化，标准流程不可能覆盖所有情况；例外需要被识别、承接并反过来修正规则。
3. **责任不是状态**：角色出现在同一系统里，不代表已经形成协同；需要明确谁发现、谁判断、谁处理、谁反馈。

### 结尾

系统的边界不是能力不足，而是它不能替组织完成理解与协同。产品的职责不是把所有事情固化成按钮，而是把业务关系表达清楚，让标准流程运行、例外被承接、责任继续传递。

## 实践来源

- SFA 评分活动：复杂的 SKU、排面、位置、价格和货龄判断，说明配置完成不等于减少一线判断负担。
- SFA 权限治理：门店不可见表面是权限问题，实际涉及组织、门店归属和业务责任关系。
- 产品协同：需求梳理、关系模型、研发协调、测试上线和问题跟踪，最终解决的是业务关系，而不是单一页面。

项目经验只作为观点来源，不写成完整项目复盘；公司、品牌和内部系统细节保持匿名。

## 页面设计

- 浅色纸张背景，与前两篇保持系列一致。
- 首屏使用大标题、核心判断和“系统步骤 / 真实流程”对照。
- 中间使用三个编号段落，每段采用“断点说明 + 正文 + 实践来源”三栏结构。
- 结尾使用浅色总结区，形成与第二篇深色结尾不同的视觉节奏。
- 桌面端三栏，移动端改为编号、正文、来源纵向排列。

## 动效

- 对照区两列随滚动交错显露，强化系统与真实流程的差异。
- 三个断点按顺序进入，编号和强调句先出现，正文随后出现。
- 实践来源保持轻量，不使用持续漂浮动效。
- 需要进入具体项目时，继续复用圆弧证据空间。
- `prefers-reduced-motion` 下保留内容层级，关闭位移与过渡。

## 边界与验收

- 不新增案例，不重写第一、第二篇文章。
- 不把文章写成权限配置教程或项目复盘。
- 三篇递进关系清楚：数据价值、组织改变、业务流程。
- 页面能在首屏说明核心判断；三段正文分别对应判断、例外、责任；移动端无横向溢出。
- 保持现有测试、lint 和 `/notes` HTTP 200。
